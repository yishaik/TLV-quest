# Production-like load gate

This gate exercises the release candidate with exactly 30 participants in 10
pre-created teams. All 30 players submit the same checkpoint concurrently with
independent idempotency keys. The expected result is one accepted progression
and two controlled stale-action conflicts per team, followed by a replay of
each winning action with its original key.

The test must use an isolated disposable run:

- one text checkpoint with no location, scan, photo, or external-message
  dependency;
- ten pre-created teams named `P0 Load Team 01` through
  `P0 Load Team 10`;
- three participants per team and no phone numbers;
- a fixed score of 100 with no speed bonus;
- a `settings.purpose` marker of `release-candidate-load-test`;
- an active release-candidate Preview origin, never a production alias unless
  the owner explicitly sets `LOAD_TEST_ALLOW_PRODUCTION=true`.

Run it through the manually dispatched `Production-like load gate` workflow.
The `production-load-test` environment supplies `LOAD_TEST_ANSWER`; the answer
must match the disposable checkpoint and must not be reused by real content.
The workflow intentionally joins only five players per minute so the gate also
proves that the public join limit is enforced rather than bypassed.

For a protected Vercel Preview, first open a temporary authenticated share URL
into a private Netscape-format cookie jar and pass its path as
`LOAD_TEST_COOKIE_FILE`. The runner reads the cookie without printing it; never
upload that file as workflow evidence.

Success requires:

- 30 successful joins distributed as three players across each of ten teams;
- all participants observing the active checkpoint before the race;
- exactly ten accepted answers and twenty HTTP 409 concurrency conflicts;
- exactly ten successful idempotent winner replays;
- every team finishing with `completed_count = 1` and `score = 100`;
- database evidence of one accepted event and one submission per team, plus
  the corresponding private Realtime event projection.

After retaining the JSON workflow artifact and database count evidence, delete
the run by its exact ID and verify that no rows remain in participants, teams,
submissions, events, outbox, presence, or Realtime authorization tables. Never
use a broad marker-only delete. Migrations
`20260730210000_allow_game_run_deletion.sql` and
`20260730211000_guard_realtime_event_parent_deletes.sql` keep Realtime triggers
from creating impossible child events after their run or team parent has been
deleted.

Webhook retry behavior is covered independently by `tests/outbox-worker.test.ts`
because this gate deliberately creates no phone registrations and must not send
external messages. The authenticated Realtime authorization smoke remains in
`.github/workflows/realtime-production-smoke.yml`; this gate verifies the event
projection generated by concurrent writes.
